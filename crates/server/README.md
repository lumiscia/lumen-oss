# lumen-server

`lumen-server` provides the Lumen render library plus a small local HTTP binary.

For production usage, the smoothest path is the hosted platform at [lumiscia.com](https://lumiscia.com). Self-hosting this crate is possible, but you will still need GPU machines, queueing, artifact storage, auth, deployment, and monitoring.

This crate is experimental and its library API may change.

## Platform Notes

Native rendering requires a GPU.

Supported targets today are:

- Linux with Vulkan rendering and optional CUDA/NVENC interop when built with `vulkan,cuda`.
- macOS with Metal rendering and VideoToolbox-oriented media paths when built with `metal`.

## Targets

`lumen-server` ships both:

- a library target, `lumen_server`, whose `render` module renders a project payload to an MP4 for embedding in custom render platforms
- a binary target, `lumen-server`, for local HTTP rendering

The exposed Axum API is intentionally binary-owned. The HTTP binary accepts the same public render payload shape as the hosted Lumen API:

```json
{
  "composition": {
    "timeline": { "fps": 30, "duration_frames": 120 },
    "render_settings": { "width": 1280, "height": 720 },
    "nodes": [
      { "id": 1, "type": "media_in", "params": { "kind": "image", "source": "hero" } },
      { "id": 2, "type": "media_output" }
    ],
    "connections": [{ "from_node": 1, "from_port": "output", "to_node": 2, "to_port": "source" }]
  },
  "media": {
    "hero": "https://example.com/hero.png"
  }
}
```

`quality` and `codec` are optional. `quality` names a preset: `draft`, `standard`, `high` and `lossless` exist on every host, and the [quality config](#quality-config) can add others. `codec` is `h264`, `hevc` or `av1`. Each wins over the composition's `render_settings.quality` and `render_settings.codec`, which win over the config's defaults, then `standard` and `h264`.

```json
{ "composition": { "...": "..." }, "quality": "high", "codec": "hevc" }
```

They're resolved when the render is requested, with the same resolver the render uses. A preset this host doesn't define, a codec none of the encoders it tries has settings for, or a codec other than the one `LUMEN_VIDEO_ENCODER`'s encoder writes returns `422` with the code `invalid_quality`.

Inside the composition, media nodes and audio clips reference either a manifest alias (`"hero"`), whose URL the render downloads, or [uploaded media](#media-uploads) as `asset:<id>`. They never name a URL directly. The self-hosted server does not implement artifact staging, provider progress callbacks, billing, accounts, durable queueing, or durable artifact storage; it renders in a local background task, stores the MP4 artifact in memory, and exposes it at `GET /renders/:id/artifact`.

`POST /renders` validates the request before accepting it. A composition that does not parse, an invalid manifest, an `asset:` reference to media this server doesn't have or of the wrong kind, or a `quality` or `codec` this host can't serve returns `422`. `webhookUrl` returns `400` with the code `webhooks_unsupported`, because this server does not deliver webhooks. A body over 2 MiB returns `413` with the code `request_too_large`, and a body that is not the expected JSON returns the matching `4xx` with the code `invalid_request_body`. Render IDs are always generated by the server.

A failed request answers with its status and `{ "code": "...", "error": "..." }`. A composition that does not parse, or names an asset it can't use, is a `422` with the code `invalid_project_payload` and a `diagnostics` array of everything wrong with it, at most 50:

```json
{
  "code": "invalid_project_payload",
  "error": "unknown param `paintt` on node 1; node 2: unknown or unsupported node type `sparkle`",
  "diagnostics": [
    {
      "severity": "error",
      "code": "node.unknown_param",
      "path": "/nodes/0/params/paintt",
      "node": 1,
      "message": "unknown param `paintt` on node 1"
    },
    {
      "severity": "error",
      "code": "node.unknown_type",
      "path": "/nodes/1/type",
      "node": 2,
      "message": "node 2: unknown or unsupported node type `sparkle`"
    }
  ]
}
```

`POST /renders/check` takes the same body as `POST /renders` and checks the composition without rendering it or downloading its media. It answers `200` with `{ "ok": false, "diagnostics": [...] }`, where `ok` is `false` only when there is an error. Warnings, such as `font.fallback` for a text family no font answers to, leave it `true` and never fail a render. Fonts resolve as a render on this host would: from `LUMEN_FONT_DIR`, the system fonts, or a manifest alias the composition names as a family. `asset:` references are checked against the uploaded media, with the same `asset.not_found` and `asset.wrong_kind` errors a render would be refused with. An invalid manifest returns `422`, as it does for `POST /renders`; `quality` and `codec` are not checked.

`path` is a JSON pointer into the composition, `node` the node's id when there is one, and `message` free-form, trimmed and cut at 1024 characters like every error message. Codes are public and stable; clients must accept codes they don't know. The [engine README](../engine/README.md#diagnostics) lists the codes, the compatibility rules, and what only a render finds.

A render that fails after being accepted keeps why. `GET /renders/:id` and `GET /renders/:id/progress` return it as `render.error`: `{ "code": "...", "message": "...", "retryable": false }`. The `progress` object has the same as `error`, `errorCode` and `retryable`, and the WebSocket's `render.failed` event carries it as `error`.

`GET /renders/:id/artifact` returns `409` with `artifact_not_ready` until the render succeeds, and `409` with the render's own error code if it failed. A succeeded render also reports the artifact's relative URL as `render.outputUrl`. `render.status` is `queued`, `processing`, `succeeded` or `failed`.

S3-compatible artifact storage is planned for a future self-hosted release. For now, the HTTP binary's in-memory artifact storage is intended for local development and single-process testing, not durable production delivery. Only the most recent `--retained-renders` finished renders (default 16, `LUMEN_SERVER_RETAINED_RENDERS`) are kept, and their artifacts stay in memory until then. Older renders are dropped, record and artifact together, and return `404`.

Renders run in submission order, `--max-concurrent-renders` at a time (default 1, `LUMEN_SERVER_MAX_CONCURRENT_RENDERS`). Later renders stay `queued` until a slot frees. Raise it only if the GPU has the memory for parallel renders. A running render also waits before its first frame while others hold most of the Vulkan contexts NVIDIA's driver allows a process: at most 14 NVENC renders or `h264_vulkan` renders that keep frames on the GPU, 9 `h264_vulkan` renders that upload frames, or 6 of those with hardware decode. GPU memory can still run out first. Renders then usually fail with an error, but it has also hung the driver on a Blackwell card, so stay within what the card's memory holds.

### Quality config

`--quality-config` or `LUMEN_QUALITY_CONFIG` names a JSON file that sets the defaults, the encoders each codec tries, and the presets' settings per encoder. It is checked when the server starts, which fails on unknown fields or codecs, an encoder this FFmpeg doesn't have or that writes another codec, settings an encoder can't use, and `options` an encoder doesn't have or whose value it rejects. Whether hardware accepts a value is only known when the encoder opens.

```json
{
  "default_preset": "standard",
  "default_codec": "h264",
  "codecs": {
    "hevc": { "encoders": ["hevc_nvenc", "hevc_vulkan", "libx265"] }
  },
  "presets": {
    "standard": {
      "encoders": { "h264_vulkan": { "qp": 23 } }
    },
    "archive": {
      "codec": "hevc",
      "encoders": {
        "hevc_nvenc": {
          "crf": 17,
          "preset": "p7",
          "options": { "tune": "hq", "rc-lookahead": "32" }
        },
        "libx265": { "crf": 16, "preset": "slower" }
      }
    }
  }
}
```

- `codecs.<codec>.encoders` is the order a codec's encoders are tried in, and the first that opens wins, with a warning for each that didn't. Without it, Linux tries `<codec>_vulkan` then `libx264`, `libx265` or `libsvtav1`, macOS tries `h264_videotoolbox` or `hevc_videotoolbox` then the same software encoders, and elsewhere only the software encoder. NVENC is only tried when named here or in `LUMEN_VIDEO_ENCODER`.
- A preset's `encoders` are keyed by FFmpeg encoder name. Each sets at most one of `crf`, `qp` and `bitrate` (bits per second, or text such as `"14M"`), plus an optional `preset`, which lumen translates for the encoder: `crf` is `rc=vbr` plus `cq` on NVENC, and `qp` is `rc_mode=cqp` on Vulkan. `options` are FFmpeg AVOptions, set after those, and may not repeat a key they set. Startup checks each option's name and, for numbers and named values, its range. Free-text values such as libx264's `tune` or `profile` are only checked when the encoder opens, so a bad one fails renders instead of startup.
- A render only tries the encoders its preset has settings for, so `lossless` skips to an encoder that is truly lossless: `libx264` (`qp` 0), `libx265` (`x265-params lossless=1`) and NVENC H.264 and HEVC (`tune=lossless`).
- An entry for a built-in preset replaces that encoder's built-in settings, and other encoders keep theirs. A custom preset's `codec` applies when neither the request nor the composition names one.
- `LUMEN_VIDEO_ENCODER` pins one encoder with no fallback. A preset without settings for it, or a codec it doesn't write, returns `422`.

The built-in settings are in `crates/ffmpeg/src/encode/preset.rs`.

### Media uploads

Files can be uploaded once and then named in any number of compositions as `asset:<id>`, in `media_in`'s or `model_3d`'s `source`, an audio clip's `source_id`, or a text node's or span's `font_family`. Every Lumen host takes the same reference form, so a composition doesn't change between this server and the hosted API. A document never carries a URL or presigned link, and an id names the same bytes for as long as it exists, so it is safe to cache renders on.

Each file is checked once, when its bytes are complete, by opening it with the decoders renders use: binary glTF (`.glb`) models with the model reader; TrueType and OpenType fonts with the font loader; PNG, JPEG, GIF, WebP, BMP, TIFF and ICO with the image decoder; anything else with FFmpeg as video or audio. The file name and declared content type play no part. A file that opens becomes `validated` with its `kind` (`image`, `video`, `audio`, `font` or `model`) and `metadata`; one that doesn't becomes `rejected` with a `rejectionReason`. WOFF fonts and everything renders refuse, such as playlists, are rejected.

| Route                                                  | Body                                         | Answers                                     |
| ------------------------------------------------------ | -------------------------------------------- | ------------------------------------------- |
| `POST /media`                                          | `{ "contentType", "fileName", "sizeBytes" }` | `201` `{ "media", "uploadUrl" }`, `pending` |
| `PUT /media/:id/content`                               | the file's bytes                             | `200` `{ "media" }`, checked                |
| `POST /media/:id/multipart`                            | none                                         | `201` `{ "uploadId" }`                      |
| `PUT /media/:id/multipart/:uploadId/parts/:partNumber` | one part's bytes                             | `200` `{ "etag", "partNumber" }`            |
| `POST /media/:id/multipart/:uploadId/complete`         | `{ "parts": [{ "etag", "partNumber" }] }`    | `200` `{ "media" }`, checked                |
| `POST /media/url`                                      | `{ "url", "fileName"? }`                     | `201` `{ "media" }`, checked                |
| `GET /media/:id`                                       |                                              | `200` `{ "media" }`                         |
| `GET /media/:id/content`                               |                                              | `200` the validated bytes                   |
| `DELETE /media/:id`                                    |                                              | `204`                                       |

A file is sent in one `PUT` to its `uploadUrl`, or in parts. Part numbers run from 1 to 10000, a part sent again replaces the earlier one, and `complete` joins the parts it lists, in ascending order, with the etags their uploads returned. Either way the bytes must add up to `sizeBytes`, which is at most `--media-max-bytes`. What a media's uploads hold on disk never passes `sizeBytes`: stored parts, parts and bodies still arriving, and a replaced part until its replacement is stored all count, and a body that would pass it is refused with `413` as it arrives. A body whose client goes away stops counting. At most `--media-max-pending` media, 100 by default, wait for their content at once: past it, `POST /media` answers `503` with `media_upload_limit` until one is checked, deleted or expires. URL imports don't count, since each ends with its request. The TypeScript SDK's `uploadMedia` and `createUrlMedia` work against these routes unchanged.

```json
{
  "media": {
    "id": "m_6f1c2a9e0b5d4e7f8a3b1c2d3e4f5a6b",
    "contentType": "video/mp4",
    "createdAt": "2026-11-08T12:00:00Z",
    "expiresAt": "2026-11-09T12:00:00Z",
    "fileName": "intro.mp4",
    "objectKey": null,
    "rejectionReason": null,
    "sizeBytes": 1843200,
    "sourceType": "upload",
    "sourceUrl": null,
    "status": "validated",
    "uploadedBytes": 1843200,
    "kind": "video",
    "metadata": {
      "width": 1920,
      "height": 1080,
      "durationMs": 4000,
      "fps": 30.0,
      "frameCount": 120,
      "codec": "h264",
      "hasAudio": true
    }
  }
}
```

Images report `width` and `height`; audio `durationMs`, `sampleRate` and `channels`; fonts their `families` and `faces`, each with its `family`, `weight` and `style`. A font asset is one family, and weight and style choose among its faces.

`POST /media/url` downloads the file once, through the same address checks and `--allow-media-host` list as manifest downloads, and keeps it like an upload. `fileName` defaults to the URL's last path segment.

`GET /media/:id/content` serves the file with its declared content type only when that agrees with its kind, and as `application/octet-stream` otherwise, with `X-Content-Type-Options: nosniff`.

Only `validated` media resolves. An id that is unknown, expired, deleted, `pending` or `rejected` is `asset.not_found`, and media of another kind than the field reads, such as an image as a video, is `asset.wrong_kind`. Both are refused when the render is requested.

Media is kept in `--media-dir`, one directory per id, and survives a restart until it expires; multipart uploads in progress don't. Files and records are written to a temporary file and renamed into place. Each upload expires `--media-ttl` after it was created, as its `expiresAt` says. From then on every lookup treats it as missing, and a sweep deletes it within a minute, or within the TTL when that is shorter. A render keeps each asset it resolves until it ends: the references in its composition when it is accepted, and any an expression names while it renders. A `DELETE` removes the media's record before it answers, so it stays deleted after a restart. Media that expires or is deleted while a render holds it reads as missing to everything else, and is removed once the last render holding it ends.

The default `--media-dir` is under the system temp directory, which can be cleared, so set it to persistent storage when using a long `--media-ttl`.

Media errors use these codes: `media_not_found` (`404`), `media_already_uploaded`, `media_upload_in_progress` and `media_not_validated` (`409`), `media_too_large` (`413`), `media_size_mismatch` and `invalid_upload_parts` (`400`), and `upload_not_found` (`404`). A URL import that fails answers with the download's own code, such as `media_download_forbidden_host`.

### Media and fonts

A render reads manifest media from one place: a directory created for that job, holding only the files downloaded from its manifest. A composition without a manifest gets an empty directory, so any source that is not a manifest alias fails, including relative paths, absolute paths, and `file://` URLs. Sources are matched after resolving symlinks.

Video and audio are only read from containers that keep their data inside the file:

- **Video:** MP4 and MOV, plus Matroska and WebM, MPEG-TS, MPEG-PS, AVI, FLV, ASF/WMV, Ogg, MXF, and IVF. Raw H.264 and HEVC streams carry no duration, so they fail to open. Put them in a container first.
- **Audio:** MP3, AAC, WAV, W64, FLAC, AIFF, CAF, AC-3, E-AC-3, DTS, AMR, and WavPack, plus the audio forms of the containers above.
- **Stills read as video:** PNG, JPEG, WebP, BMP, and TIFF hold one frame for the whole clip. GIF and APNG play their animation. Other image formats, such as TGA, EXR, and SVG, are refused.

Formats that point at other files or hosts are refused, including HLS, DASH, concat lists, image sequences, and SDP, because they could read outside the job directory. Images on `media_in` nodes with `kind: "image"` are decoded from their bytes without FFmpeg.

Each job's manifest is limited to 256 entries, 512 MiB per file, and 2 GiB in total. Aliases can use up to 128 letters, digits, `.`, `_`, and `-`, and can't be only dots. Decoding decides whether a file is usable, so the response `Content-Type` is not checked.

Downloads refuse hosts that resolve to private, loopback, link-local, and other non-public addresses. The check runs on every connection, so it covers DNS rebinding and redirects. Up to 5 redirects are followed. Environment proxy settings are ignored. To download from an internal host, list it as it appears in the URL with `--allow-media-host` (repeatable; `LUMEN_SERVER_ALLOW_MEDIA_HOSTS` takes a comma-separated list).

Fonts are found by the family name inside each font file, not by file name, in the same order as `lumen-local`:

- a font staged in the job's manifest, named by its alias (`"font_family": "<alias>"`).
- the directory `LUMEN_FONT_DIR` names, if set. The server refuses to start if it isn't a directory. It is scanned once per render.
- the installed system fonts, scanned the first time a family isn't found above and then kept for the life of the process. The family `Roboto` skips this step, so it is always the bundled font unless the directory has one.

A family that none of them has is logged once per render as a warning, and text using it falls back to the bundled font. A composition can only read fonts that are in the font directory or the system fonts, never other files on the server. A font directory is trusted, so it follows symlinks.

`GET /renders/:id/progress` and `GET /renders/:id/socket` mirror the hosted progress shape. The WebSocket sends the render's current status when it connects, then each change, and closes after the render succeeds or fails. It sends SDK render events like:

```json
{
  "type": "render.progress",
  "renderId": "r_123",
  "progress": 0.42
}
```

The binary exposes:

- `GET /health`
- `POST /renders`
- `POST /renders/check`
- `GET /renders/:id`
- `GET /renders/:id/progress`
- `GET /renders/:id/socket`
- `GET /renders/:id/artifact`
- `POST /media`, `POST /media/url`, `GET /media/:id`, `DELETE /media/:id`, `PUT` and `GET /media/:id/content`, and the multipart routes under `/media/:id/multipart`, described in [Media uploads](#media-uploads)

Run it with:

```bash
cargo run -p lumen-server --features cli --bin lumen-server -- --bind 127.0.0.1:8080
```

When using the TypeScript SDK against the local server, set the SDK base URL to `http://127.0.0.1:8080`.

Set `--token` or `LUMEN_SERVER_TOKEN` to require `Authorization: Bearer ...` on every route except `/health`, including the WebSocket. The check runs before the request body is read. The server exits with an error if it is asked to bind a non-loopback address without a token. An empty token counts as no token.

Progress WebSocket updates are coalesced by default. Set
`--progress-min-delta` or `LUMEN_SERVER_PROGRESS_MIN_DELTA` to control the
minimum progress increase required before another non-terminal progress event is
broadcast. The value is a `0.0` to `1.0` fraction; the default is `0.02`.
Terminal updates, state changes, and stage changes are still broadcast
immediately. Set it to `0` to emit every renderer progress update.

Set `RUST_LOG=lumen_server=debug` for detailed per-frame render progress logs
and CUDA/Vulkan device diagnostics.

The renderer logs the selected adapter name, backend, device type, vendor,
device, driver, and driver details when a render starts. For software Vulkan or
non-NVIDIA validation, the same adapter-selection knobs used by `wgpu` are
available:

```bash
LUMEN_GPU_FORCE_FALLBACK_ADAPTER=1 \
WGPU_BACKEND=vulkan \
WGPU_POWER_PREF=none \
cargo run -p lumen-server --features cli,vulkan --bin lumen-server
```

On Linux CI, the SDK integration test also points Vulkan at lavapipe with
`VK_ICD_FILENAMES=/usr/share/vulkan/icd.d/lvp_icd.json`. This is a portability
baseline, not a hardware performance target.

### Flags and environment

| Flag                              | Environment                           | Default                     | Meaning                                                                                           |
| --------------------------------- | ------------------------------------- | --------------------------- | ------------------------------------------------------------------------------------------------- |
| `--bind <addr>`                   | `LUMEN_SERVER_BIND`                   | `127.0.0.1:8080`            | Address to listen on. A non-loopback address requires a token.                                    |
| `--token <token>`                 | `LUMEN_SERVER_TOKEN`                  | none                        | Bearer token required on every route except `/health`.                                            |
| `--max-concurrent-renders <n>`    | `LUMEN_SERVER_MAX_CONCURRENT_RENDERS` | 1                           | Renders that run at once.                                                                         |
| `--retained-renders <n>`          | `LUMEN_SERVER_RETAINED_RENDERS`       | 16                          | Finished renders kept in memory.                                                                  |
| `--allow-media-host <host>`       | `LUMEN_SERVER_ALLOW_MEDIA_HOSTS`      | none                        | Hosts allowed to resolve to non-public addresses. Repeatable, or comma-separated in the variable. |
| `--progress-min-delta <fraction>` | `LUMEN_SERVER_PROGRESS_MIN_DELTA`     | 0.02                        | Minimum progress increase between non-terminal updates.                                           |
| `--media-dir <path>`              | `LUMEN_SERVER_MEDIA_DIR`              | `<temp>/lumen-server-media` | Directory uploaded media is kept in, created if missing.                                          |
| `--media-ttl <duration>`          | `LUMEN_SERVER_MEDIA_TTL`              | `24h`                       | How long uploaded media is kept: seconds, or a number with `s`, `m`, `h` or `d`.                  |
| `--media-max-bytes <n>`           | `LUMEN_SERVER_MEDIA_MAX_BYTES`        | 2147483648                  | Largest uploaded or imported file.                                                                |
| `--media-max-pending <n>`         | `LUMEN_SERVER_MEDIA_MAX_PENDING`      | 100                         | Most media waiting for its content at once. More are refused with `503`.                          |
| `--verbose-debug`                 | `LUMEN_SERVER_VERBOSE_DEBUG`          | false                       | Per-frame renderer diagnostics.                                                                   |
|                                   | `LUMEN_FONT_DIR`                      | none                        | Directory of fonts, looked up before the system fonts. Must exist.                                |
|                                   | `LUMEN_VIDEO_ENCODER`                 | platform default            | Encoder name, used when the render options name none.                                             |
|                                   | `LUMEN_HARDWARE_DECODE`               |                             | `1`, `true`, `yes` or `on` turns GPU video decode on, and any other value turns it off.           |
